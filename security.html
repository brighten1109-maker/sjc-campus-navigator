Protect the access.

This module adds a working password-security demonstration to the SJC Campus Navigator. Passwords are never stored directly; a random salt and a slow PBKDF2 key-derivation process are used to create a verification hash.

03 / ALGORITHM

How the protection works.

The implementation demonstrates the same core principles expected in a real authentication system: random salts, a password-specific key-derivation function, constant-time comparison and no plain-text password storage.

01Validate

Check length and strength before accepting the credential.

02Salt

Generate a fresh 16-byte random salt for the credential.

03Derive

Use PBKDF2 with SHA-256 and 310,000 iterations.

04Store

Store only username, salt, iterations and derived hash locally.

05Verify

Derive a new hash and compare it byte-by-byte without exposing the password.

04 / SECURITY SPECIFICATION

Implemented controls

  • Minimum 12-character password policy
  • Uppercase, lowercase, number and special-character checks
  • Random 128-bit salt using crypto.getRandomValues()
  • PBKDF2 password derivation using SHA-256
  • 310,000 derivation iterations
  • 256-bit derived key
  • No plain-text password stored
  • Session flag cleared by the logout action
05 / PRODUCTION NOTE

What would change in production?

This page is intentionally a front-end security demonstration for Module 3. A production SJC administration system should move credential storage and authentication to a trusted backend, use HTTPS, server-side sessions or secure tokens, rate limiting, audit logging and a database. The client must never be treated as the security boundary.

Important: localStorage is used only so the Moodle demonstration can run on GitHub Pages without a backend. Do not use this client-only credential store for real institutional accounts.
